# Research the cause, prove a coupon, then apply

1. Inspect native target/current/control crops. State a falsifiable cause: “surface lacks a reflected source” rather than “needs realism.” Separate morphology, reflectance, illumination, mapping and display. Vision can identify a failed appearance but cannot prove an absent node or object.
2. Search current primary documentation and a relevant artist explanation. Inspect installed APIs/versions before reusing a tutorial. Record citations, retrieved claim, local applicability, licence and what remains untested in RESEARCH-NOTES. Do not present source availability, a successful install or a paper score as local quality evidence.
3. Build the smallest coupon plus a one-variable counterfactual. Freeze scale, seed, view, exposure and light; use both neutral diagnostics and the production fixture where useful. Test one mechanism rather than a complete redesign. In UI this is an isolated component in the actual typography/layout environment; in Three.js a material/geometry patch under the same renderer and tone mapping.
4. Save code, inputs, settings, actual output, measurements and hashes. Inspect the result. Distinguish API/render PASS, mechanism PASS and owner/integration acceptance. A valid optical construction can still be the wrong shape/art style.
5. Publish the verified mechanism with control, limits and exact dependency versions promptly so lanes can reuse it. Apply only that mechanism to an authorized fixture copy. Re-test actual receiver coverage, final-scale detail and protected deltas in context.
6. After two failed focused trials, change the hypothesis/representation or ask for owner direction. Do not keep replacing a working library with a new tool because the morphology is wrong.

## Representation and sourcing checks

- Prefer existing editable assets/native tools when they fit the requested style; procedural versus scan is a per-component decision, not ideology. Match morphology and scale, not asset names. Retain source and license, including model weights/output and asset redistribution terms separately from code license.
- Treat single-image intrinsic/material recovery as underdetermined. Generated albedo/height/roughness are hypotheses; an RGB highlight is not automatically an albedo mark or a height ridge. Derive/co-generate corresponding maps, keep transforms aligned, and relight to expose baked illumination. Do not ask an image model for unrelated four-panel “PBR” maps and call them aligned measured channels.
- For extraction: isolate approved homogeneous samples → rectify planar regions → assess lighting removal → synthesize seamless coherent coverage → derive/bake aligned maps → test metric scale. Preserve source registration and avoid grazing/nonplanar “rectification” claims. Direct target-pixel use needs separate authorization.
- Projection is a legitimate owner-approved fixed-view branch, not arbitrary-view reconstruction. Keep an explicit projector and visibility mask; test another view and name the failure envelope. Do not replace real 3D work with an unapproved paint-over.
- Use final-output pixel density before expensive full renders. Detail absent from the target must be authored/sourced, not “recovered.” Keep one coherent master for zoom levels, with downsampled parity to the approved hero.
- Verify access/scopes and budget with a bounded probe before planning around an external service. Never silently substitute a paid route or upload private inputs. Keep install experiments in isolated environments; no production dependency downgrade for an unqualified research tool.

Blender mechanism recipes belong in `blender-lookdev-recipes`; geometry/projection/ray/UV procedures belong in `blender-reference-match-loop`. See [domain packs](domain-packs.md) for their contracts, not copied scene constants.
